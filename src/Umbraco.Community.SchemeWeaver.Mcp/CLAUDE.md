# CLAUDE.md

Guidance for Claude Code when working in the SchemeWeaver MCP server project.

## Overview

TypeScript MCP server (stdio transport) exposing SchemeWeaver's management API as tools, built on `@umbraco-cms/mcp-server-sdk`. Scaffolded from `@umbraco-cms/create-umbraco-mcp-server`, trimmed of the Cloudflare-worker/hosted, MCP-chaining and eval-test template features.

## Commands

```bash
npm run build          # tsup → dist/, then tool-types codegen
npm run compile        # type-check only
npm run generate       # extract SchemeWeaver OpenAPI subset from running instance + Orval client gen
npm test               # integration tests (need running TestHost + .env credentials)
npm run inspect        # MCP inspector

node --env-file=.env dist/index.js --list-tools
node --env-file=.env dist/index.js --call <tool> --call-args '{"json":"args"}'   # note: --call-args, not --args
node --env-file=.env scripts/setup-api-user.mjs <admin-email> <admin-password>   # create the API user in a fresh TestHost DB
```

**Always use npm scripts** for build/test — never run `tsc`/`jest` directly.

## Structure

```
src/
├── umbraco-api/
│   ├── api/
│   │   ├── client.ts                    # Orval mutator → SDK's UmbracoManagementClient (OAuth client_credentials)
│   │   ├── schemeweaver-openapi.json    # extracted spec (committed; regenerated by npm run generate)
│   │   └── generated/                   # Orval output: typed client + Zod schemas — do not edit
│   └── tools/
│       ├── schemeweaver/                # the 16 SchemeWeaver tools (get/ post/ delete/ + __tests__/)
│       └── umbraco-server/              # get-server-info (auth smoke test)
├── config/                              # server-config, slice-registry, mode-registry
├── mocks/                               # MSW infra (only active when USE_MOCK_API=true; currently no handlers)
├── collections.ts                       # in-process chaining export
└── index.ts                             # entry point (registers collections, server instructions)
scripts/
├── extract-openapi.mjs                  # management.json → SchemeWeaver-only spec
└── setup-api-user.mjs                   # creates the API user via admin login + PKCE flow
```

## Conventions & gotchas

- One file per tool in `get/`/`post/`/`delete/`; export `withStandardDecorators(tool)`; `inputSchema` is a Zod **shape** (not `z.object()`); array responses go through `executeGetItemsApiCall` which wraps as `{ items }`.
- Tool descriptions are the prompt surface — they carry the SchemeWeaver domain model (sourceType values, `__name`/`__url` built-in aliases, IdOverride tokens, resolverConfig JSON shapes). Keep them accurate when the C# model changes.
- The schema-properties endpoints return **PascalCase** names (`Headline`); saved mappings conventionally use camelCase (`headline`); the C# setter matches case-insensitively.
- Umbraco 18 serves OpenAPI at `/umbraco/openapi/management.json` (not `/umbraco/swagger/...`).
- Umbraco's backoffice OAuth redacts codes/tokens into cookies (`__Host-umbPkceCode`, `__Host-umbAccessToken`) and expects the literal string `[redacted]` in their place — `scripts/setup-api-user.mjs` implements this dance; don't "fix" it.
- Integration tests hit the real instance from `.env`; the round-trip test must only ever map a content type that has **no existing mapping** (TestHost fixture mappings are sacred) and must delete it afterwards.
- `.env` is gitignored and holds the API user credentials; `.env.example` is the committed reference.
